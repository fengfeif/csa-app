1. 安装与启动

系统要求

项目最低要求
操作系统macOS 12.0 (Monterey) 及以上
芯片架构Apple Silicon (M1/M2/M3/M4) 或 Intel
内存4 GB 以上
磁盘空间50 MB（应用本体）
网络需要联网（查询 CVE/EOL 数据）

安装步骤

  1. 将 组件安全研判.app 拖入 /Applications/（访达左侧"应用程序"文件夹）
  2. 首次打开时，macOS 会提示"无法验证开发者"。点击 取消，然后打开 系统设置 → 隐私与安全性，在底部点击 仍要打开
  3. 再次双击应用，在弹出的确认框中点击 打开
  4. 应用启动后即可使用
注意：首次启动需联网。应用需要访问 search.maven.org、endoflife.date、api.deepseek.com 等外部服务，请确保网络通畅。

卸载

将 组件安全研判.app 从 /Applications/ 拖入废纸篓即可。应用不在系统中残留任何配置文件。

2. 功能概览

组件安全研判是一个桌面工具，用于对开源软件组件进行安全漏洞和生命周期（EOL）评估。主要功能：

单组件研判 可选

输入组件名和版本号，对单个组件进行完整的 8 步安全研判流程。

批量研判 核心

支持从 Excel 导入组件清单（最多数百个），5 个并发研判，批量生成漏洞和 EOL 报告。

AI 兜底 智能

当自动化数据源（endoflife.date、Maven Central、GitHub）都查不到时，调用 AI 模型进行 EOL 判定。

报告导出 核心

支持导出 Excel 格式的安全检测报告，包含漏洞详情和 EOL 状态。

3. 单组件研判

输入格式

字段必填格式示例
组件名称是artifactId 或 groupId:artifactIdlog4j-core 或 org.apache.logging.log4j:log4j-core
版本号是语义化版本号2.17.1
厂商/组织否组织名称Apache

研判流程（8 步）

步骤名称说明
1CPE 资产匹配在 NVD 数据库中匹配组件的 CPE 标识
2CVE 漏洞检索检索该组件版本已知的安全漏洞
3官方公告核验核验漏洞的官方公告和影响范围
4GitHub Release检查 GitHub 上的最新发布版本
5AI 深度分析AI 分析组件的安全状态
6生命周期文档查阅 endoflife.date 获取生命周期信息
7维护规则提取从内部规则库匹配组件维护状态
8EOL 终止判定综合所有数据源判定 EOL 状态

操作步骤

  1. 在"单组件研判"页签下，填写组件名称和版本号
  2. 点击 开始研判
  3. 研判过程中，8 个步骤图标会依次变为绿色（完成）或灰色（跳过）
  4. 研判完成后，下方自动展示漏洞风险和 EOL 生命周期结果
  5. 点击 导出 Excel 报告 可导出完整报告

4. 批量研判与 Excel 导入

Excel 导入格式

Excel 文件需包含一个名为 检出组件信息 的工作表，表头必须包含以下列：

列名说明示例
组件名称组件的 artifactId 或 groupId:artifactIdorg.apache.commons:commons-lang3
版本号组件版本3.12.0
提示：表头匹配为精确匹配，请确保列名完全一致。其他列（如厂商、检出路径等）不影响导入。

操作步骤

  1. 点击顶部 批量研判 页签
  2. 点击 导入 Excel，选择 Excel 文件
  3. 导入后，批量输入框自动填充组件清单，格式为 组件名,版本号（每行一个）
  4. 点击 批量研判全部 开始研判
  5. 研判过程中，进度条实时显示进度
  6. 研判完成后，表格展示每个组件的漏洞数和 EOL 状态
  7. 点击 导出 Excel 报告 生成完整报告

批量输入格式（手动输入）

也可以不导入 Excel，直接在文本框中手动输入：

每行一个组件，格式：组件名,版本号[,厂商]
支持 groupId:artifactId 格式

例如：
org.apache.commons:commons-lang3,3.12.0,Apache
log4j-core,2.17.1
jackson-databind,2.14.1,FasterXML

批量研判并发机制

  • 每次同时研判 5 个 组件
  • 每个组件的研判中，CPE 匹配、CVE 检索、EOL 检查 三步骤并行执行
  • EOL 缓存：同名组件不同版本只查询 1 次 endoflife.date，后续版本直接使用缓存
  • 网络请求超时控制：HTTP 请求 10 秒，AI 调用 15 秒，超时后跳过

5. AI 兜底配置

当 endoflife.date、Maven Central、GitHub 都查不到组件的 EOL 信息时，应用会自动调用 AI 模型进行兜底判定。

配置项

配置项说明默认值
API 端点OpenAI 兼容的 API 地址https://api.deepseek.com/v1/chat/completions
API KeyAPI 密钥，保存在本地预置（可替换）
模型模型名称deepseek-v4-flash
失败重试次数AI 调用失败后的重试次数2

操作步骤

  1. 点击顶部 AI配置 按钮
  2. 填写或修改 API 端点、API Key、模型名称
  3. 点击 测试连接 验证配置是否有效
  4. 连接成功后，配置自动保存到本地

AI 判定规则

  • 组件仍有新版本发布、官方活跃维护 → 维护中
  • 组件已停止维护、仅偶尔打安全补丁而无新功能开发 → 已EOL
  • 组件即将停止维护（已公布 EOL 日期且在 6 个月内）→ 即将EOL
  • 不确定时，默认判定为 已EOL（安全优先）
提示：AI 不只依赖发布时间判断。Prompt 中明确要求 AI 结合项目实际的维护活跃度、社区活跃度、是否有维护计划来综合判断。

支持的其他 AI 服务

任何兼容 OpenAI Chat Completions API 的服务都可以使用，例如：

  • DeepSeek（默认）
  • OpenAI GPT-4o / GPT-4o-mini
  • 通义千问（兼容模式）
  • 本地部署的 Ollama / vLLM

6. 数据同步与备份

导出/导入配置

应用数据保存在本地，不跨设备同步。如需迁移到其他 Mac：

  1. 点击 数据同步 按钮
  2. 点击 导出全部数据（JSON），保存 JSON 文件
  3. 在目标 Mac 上打开应用，点击 数据同步
  4. 点击 导入数据文件，选择之前导出的 JSON 文件

导出内容包括：

  • AI 配置（含 API Key）
  • EOL 缓存（30 天内有效结论）
  • 批量输入列表
  • 内部组件规则
安全警告：导出的 JSON 文件包含 API Key，请妥善保管，不要通过公开渠道传输。

清除 EOL 缓存

点击 清除EOL缓存 可清除所有已缓存的 EOL 结论。建议在以下情况使用：

  • 修改了 AI prompt 或 EOL 判定逻辑后，需要重新研判
  • 缓存数据过期，需要获取最新结果
  • 研判结果与预期不符，需要排除缓存干扰

合并多个 Excel

在"数据同步"面板中，点击 合并多个 Excel（表头不变） 可将多个结构相同的 Excel 文件合并为一个：

  • 以第一个文件为模板，保留工作表、表头、样式和列宽
  • 仅追加数据型工作表（如"检出组件信息"）的行数据
  • 结构特殊的工作表（如"导航"、"应用信息"）保留第一个文件的内容

8. EOL 判定逻辑说明

数据源优先级

EOL 判定按以下顺序查询数据源，命中即返回结果：

顺序数据源说明
1endoflife.date开源组件生命周期数据库，按版本号匹配正确的 EOL 周期
2Maven Central查询最新版本和发布时间，超过 2 年未发布 → 已EOL
3GitHub Releases查询最新发布时间，超过 2 年未发布 → 已EOL
4AI 兜底以上都查不到时，调用 AI 综合判断

判定结果

状态颜色含义
维护中绿色组件仍在活跃维护，有新版本发布
已EOL红色组件已停止维护，建议规划迁移
即将EOL橙色组件将在 6 个月内停止维护，提前规划升级
AI判定紫色由 AI 模型判定，建议人工复核
待研判紫色尚未进行 EOL 研判

版本号匹配逻辑

endoflife.date 返回多个版本周期（cycle）时，应用会按版本号前缀匹配正确的周期：

  • 用户版本 2.3.2 → 匹配 cycle 2.3（而非 2）
  • 用户版本 2.17.1 → 匹配 cycle 2.17
  • 精确匹配优先，长前缀优先于短前缀

9. 常见问题

Q: 首次打开提示"已损坏，无法打开"

这是 macOS Gatekeeper 的安全机制。打开终端，执行：

sudo xattr -cr /Applications/组件安全研判.app

输入密码后，再次双击打开即可。

Q: 研判结果显示"未知"或所有组件都标为"已EOL"

可能原因和排查步骤：

  • 网络不通：检查是否能访问 search.maven.org 和 endoflife.date
  • EOL 缓存过期：点击 清除EOL缓存 后重新研判
  • AI 配置无效：点击 AI配置 → 测试连接 验证

Q: 导入 Excel 后批量输入框内容异常

确保 Excel 文件包含 检出组件信息 工作表，且表头中有 组件名称 和 版本号 列。表头必须精确匹配，不能有前后空格。

Q: 研判速度很慢

批量研判 144 个组件通常需要 5-15 分钟，取决于：

  • 网络质量（Maven Central、endoflife.date、GitHub 的响应速度）
  • 需要 AI 兜底的组件数量（AI 调用比自动化数据源慢）
  • GitHub API 限流（每小时 60 次未认证请求）

Q: 如何切换深色/浅色主题

点击右上角的 太阳/月亮 图标切换主题。主题设置自动保存。

Q: AI 判定结果不准确怎么办

AI 兜底是最后手段，准确性取决于 AI 模型对该组件的了解程度。建议：

  • 切换更强的模型（如 deepseek-v4 或 gpt-4o）
  • 手动在单组件研判中复核 AI 判定结果
  • 对于关键组件，以 endoflife.date 或官方文档为准
